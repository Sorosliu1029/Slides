Q4: 当Q3的数组长度达到 10,000,000,000 时，以二叉搜索树作为搜索的数据结构，会遇到什么问题？

此时：数据会分布在约 10,000,000 个 disk page 上

Thought 4

  1. 在二叉树上搜索的路径会很长：log2(10,000,000) ≈ 24
  2. 每个二叉树节点的 size: 4B (int) + 8B × 2 (2个 pointer) = 20B → 每个 disk page 可存大约 4096 / 20 ≈ 204 个节点
  3. 1 和 2 结合起来，会在搜索二叉树时多次 read disk
  4. 读盘时间 >>> 读内存时间，两者速度差的量级大约在 103 级

Q5: 如何优化二叉树在上述问题中的缺点？

Thought 5

高瘦型树结构: binary tree (查找深度：log2N)

矮胖型树结构: B tree / B+ tree (查找深度：lognN)

B+ 树节点结构

Key有序，每个Key伴随一个Pointer，指向下一级树节点

举个例子：n=5

🟥：内部节点，🟩：叶子节点

内部节点 → 内部节点 / 叶子节点，叶子节点 → 磁盘页地址

B+树的特征

  • 除根节点外，每个节点至少 半满 (避免退化成高瘦型树结构）
  • 节点间保持有序 （类似二叉搜索树的要求）（搜索树的基本特征）
  • 所有叶子节点在同一深度 （高度平衡树）

Q11: 上面讨论的假设都是 unique index key，如果要建立 index 的字段取值可重复，如 user.birthday，要怎么小小地修改一下 B+ tree ?

如：2000-01-01 生日的用户有 1000 个: user1, user2, user3, ... user1000

Thought 11

  1. 对B+树节点结构不做修改
    丧失了搜索树的优点
  2. birthday: 2000-01-01 的叶子节点上指向一个 linked list: user1 -> user2 -> user3 -> ... -> user1000 -> null
  3. 让每条记录都能 unique, (birthday, id)
    查找 SELECT * FROM user WHERE birthday = 2000-01-01 时，转换为范围查询 [(2000-01-01, ID_MIN), (2000-01-01, ID_MAX)]

Q12: 怎么支持多线程同时并发查询一棵 B+ tree ?

Thought 12

  • 每个查询都排它锁根节点
  • Crab 🦀 protocol （想象螃蟹走路）
    • 读：根节点共享锁 → 沿着查找路径向下走，对每个途径的节点都加共享锁 → 落地下一级节点后，释放刚刚所在节点的锁
    • 写：根节点排它锁 → 沿着查找路径向下走，对每个途径的节点加排它锁 → 落地下一级节点后，如果该节点 安全, 则释放刚刚所在节点的锁
      怎样算安全：
      • 插入：该节点插入新数据后不会全满，即该节点不会出现分裂
      • 删除：该节点删除数据后不会半满，即该节点不会出现合并或重分配

Q13: 在查找，插入，删除操作都是 随机 的情况下，怎么优化Q12的 Crab protocol ?

Thought 13

写操作时，在路径上从上到下查找时，都用共享锁，只在实际发生写的节点上用排它锁

如果查找过程中发现节点 不安全 , 则从根节点重试，用排它锁，即 fallback 到原先的 crab protocol 写操作

原因：当n很大时，发生分裂或合并、重分配的概率是很小的

Q14: 在对一棵B+树有高频的读写操作时，怎样在操作系统层面及计算机体系结构层面做优化？

Thought 14

操作系统层面：对根节点（及第一级节点，可选）做内存缓存，并标记常驻内存，使得不会被LRU换页策略驱逐出内存

体系结构层面：在存储层级上，将根节点放到更靠近CPU的地方，如CPU的L3，乃至L2缓存中

Q15: 实际使用时，n会比较大，比方说 n=256。n 的取值怎么决定，是不是越大越好，有没有什么限制？

Thought 15

  • n大的 pros：B+tree更矮胖，lognN 更小，查找路径更短
  • n大的 cons：节点通常不是全满的，n设置的太大会导致空间浪费 / 太大了也会花费更多的读盘、写盘时间 / 花更多时间做节点内搜索
  • 同时有限制：磁盘页大小，内存页大小，L3, L2缓存大小
